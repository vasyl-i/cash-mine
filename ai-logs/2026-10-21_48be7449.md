CashMine practical task API
===========================

A test backend for the CashMine React Native practical task. All data is made up and nothing here
moves real money. Treat it like a real remote server: requests can be slow, and any request can fail.

Base URL: [REDACTED:EXPO_PUBLIC_API_URL]

Authentication
--------------

Send your token from the task email on every /v1 request:

    Authorization: Bearer <token>

Your data belongs to your token only. It starts fresh with your first request and includes about
30 days of history. The token stops working at the time given in your task email.

Conventions
-----------

- JSON in and out. Times are ISO 8601 strings in UTC.
- Amounts are decimal strings in the asset's own unit, for example "0.0005" (BTC). They are never
  JSON numbers. Each asset allows at most `decimals` decimal places. Write them as digits with an
  optional dot and more digits, and no leading zeros: "0.5" and "12" are fine; ".5", "1.", "05"
  and "1e-3" are not.
- CORS is open to any origin, so you can call the API from a web app.

Errors
------

    { "error": { "code": "VALIDATION", "message": "...", "field": "amount" } }

    HTTP  code                  meaning
    400   VALIDATION            the request is invalid; `field` names the field when there is one
    401   UNAUTHORIZED          token missing, invalid or expired
    404   NOT_FOUND             unknown endpoint or id
    409   IDEMPOTENCY_MISMATCH  an Idempotency-Key was reused with a different body
    429   RATE_LIMITED          too many requests; wait `retryAfterMs` (also the Retry-After header, in seconds)
    500   SERVER                temporary server error
    503   SERVER                temporary server error
    504   TIMEOUT               the server did not finish in time; the outcome is unknown

A 429 response looks like this:

    { "error": { "code": "RATE_LIMITED", "message": "Too many requests", "retryAfterMs": 2300 } }

Rate limits apply per token.

GET /v1/balances
----------------

    {
      "asOf": "2026-10-20T08:01:15.000Z",
      "items": [
        { "asset": "USDT", "decimals": 6, "available": "820.413207", "pending": "50.12",
          "claiming": "0", "usdPrice": "1.0002" }
      ]
    }

- available: can be claimed now
- pending: payback accrued but not yet confirmed; it becomes available once confirmed
- claiming: the amount in claims that have not completed yet
- usdPrice: the price of one unit in USD

Balances are snapshots, recomputed every 15 seconds. `asOf` is the time of the snapshot, so a claim
you just created may not show up until the next one.

GET /v1/activity?limit=20&cursor=...
------------------------------------

History, newest first. `limit` is 1 to 20 (default 20). Pass `nextCursor` as `cursor` to get the
next page; `nextCursor` is null on the last page.

    {
      "items": [
        { "id": "act_...", "type": "accrual", "asset": "USDT", "amount": "9.81", "status": "confirmed",
          "exchange": "Binance", "createdAt": "...", "relatedId": null }
      ],
      "nextCursor": "..."
    }

- type: accrual (payback earned on an exchange), reversal (an earlier accrual taken back by the
  exchange; relatedId is that accrual's id) or claim (relatedId is the claim id for claims you
  create; null for older claims)
- exchange: where the payback came from; null for claims
- amount: signed; negative for reversals and claims
- status: accrual pending | confirmed; reversal confirmed; claim pending | completed | failed

GET /v1/claim-options?asset=ETH
-------------------------------

    { "asset": "ETH", "minAmount": "0.01", "fee": "0.0012",
      "destinations": [ { "id": "dest_wallet", "label": "Wallet 0x8f3e…a91c" } ] }

The fee is taken from the claimed amount: the user receives amount minus fee.

POST /v1/claims
---------------

Headers:

    Idempotency-Key: <1 to 100 characters, required; a UUID works>

Body:

    { "asset": "ETH", "amount": "0.5", "destinationId": "dest_wallet" }

Rules: minAmount <= amount <= available, and at most `decimals` decimal places. `available` is
checked live, not against the last snapshot.

201 returns a claim. Its amount leaves `available` at once and is counted in `claiming` until the
claim settles.

Repeating a request with the same Idempotency-Key and the same body returns the original claim
(200, header `Idempotent-Replayed: true`) and never creates a second claim, even if the first
response was lost. The same key with a different body returns 409.

Claim:

    { "id": "clm_...", "asset": "ETH", "amount": "0.5", "fee": "0.0012", "receiveAmount": "0.4988",
      "destinationId": "dest_wallet", "status": "pending", "failureReason": null,
      "createdAt": "...", "updatedAt": "..." }

GET /v1/claims/{id}
-------------------

Returns the claim. A pending claim settles within about 20 seconds, to completed or failed. When a
claim fails, its amount returns to available and failureReason says why.

The last type error will go away once the claim route exists. Before writing the claim flow, the brief requires us to compare at least two approaches for how balances behave right after a claim. The constraint is that `/v1/balances` is a snapshot recomputed every 15 s, so a claim that just returned 201 may not appear in `available`/`claiming` for up to about 15 s. The server checks `available` live, so double-spending is impossible either way; the question is only what the user sees in that window.

**A. Optimistic overlay.** After the 201, subtract the claim amount from `available` and add it to `claiming` on the client. Remove the adjustment once a snapshot arrives with `asOf ≥ claim.createdAt`, or when the claim fails.
- ✅ The numbers update instantly and feel right.
- ❌ The app shows money it computed itself instead of what the server said. If the reconciliation is off, for example because of clock skew or a missed snapshot, the claim gets subtracted twice or never, which is a real correctness risk.

**B. Server numbers only, plus a progress indicator.** Never adjust balances locally. Show a "Claim of 0.5 ETH in progress" card and mark that asset's row "updating…". Refetch balances after the create and again when the claim settles.
- ✅ Simplest and fully honest: every number is the server's.
- ❌ For up to 15 s, `available` still includes the claimed amount. A second claim could fail with a 400, which is safe but confusing.

**C. Hybrid (my recommendation).** The main numbers always come from the server, as in B. Any of our own claims that the current snapshot doesn't include yet (`asOf < claim.createdAt`) appear as a note on that row, e.g. "−0.5 in a claim not yet reflected (as of 17:05:01)". The claim form's **Max** and its validation subtract those unreflected amounts, so the user can't predictably trigger the 400.
- ✅ The app never misstates what the server says, the user still sees the claim right away, and the form stays honest.
- ❌ Slightly more logic. The reconciliation rule is a small pure function and gets unit tests.

**How it works on web now**
- AsyncStorage's web version stores data in `window.localStorage`, wrapped in Promises. The token sits under the key `cashmine-auth` and claim attempts under `cashmine-claims`, both as JSON.
- It persists across reloads and tabs on the same origin, which is what the brief asks for ("keeps it in the browser").

**Swapping to MMKV**

Generating the key in `prepareAttempt` is fine. A key should belong to one logical claim (one body), so it's created the first time that body is sent and reused for every retry of it. Creating it earlier, for example when the form opens, wouldn't help: if the user changes the amount after a 400, the old key with a new body gets a 409, so a new key is needed anyway. The real gap is that nothing guarantees the key is saved before the request goes out.

**What happens now**
1. `set({ attempt })` updates memory, and zustand `persist` then calls `storage.setItem(...)` without waiting for it to finish.
2. `mutation.mutate(attempt)` sends the request.

**Web is safe today, but only by accident.** I checked the AsyncStorage web source: `createPromise` runs `localStorage.setItem` synchronously inside the Promise constructor. So on web the key is already in localStorage before `fetch` starts. Nothing in our code guarantees that, though. With native AsyncStorage or some MMKV/SecureStore wrappers the write is truly async. If the app is killed after the request is sent but before the write finishes, the key is lost. The user then claims again with a new key and could create a duplicate claim.

**Second issue: a hydration race.** The token gate waits for the auth store to load from storage, but not for the claims store. If someone submits before the claims store has loaded, the stored state would overwrite the new attempt when it arrives. That's unlikely, but it's the same class of bug.

**Proposed fix (about 10 min)**
- Add a small `src/store/claim-attempt-storage.ts`, separate from zustand, with `saveAttempt`, `loadAttempt` and `clearAttempt`, each using `await storage.setItem(...)` directly.
- Make `prepareAttempt` async and have it save the attempt before returning it, so `submit` waits for the save before calling `mutate`. The rule becomes "saved before sent", and it holds on every storage backend.
- The zustand store keeps an in-memory copy for the UI and stays the source of truth for tracked claims.
- Make the claim screen wait for claims-store hydration, as the gate does for auth.
- Add a unit test that the save finishes before `createClaim` is called.
